# doc-extractor

Сервис/CLI: текст документа (счёт, КП, акт) → JSON по фиксированной схеме.
Главная цель — не выдумывать то, чего нет в документе.

> Статус: пайплайн, grounding, тестовый набор и eval готовы. Результаты прогона на модели — TODO.

## Требования

- Python 3.12
- [uv](https://docs.astral.sh/uv/) (сам создаёт `.venv` и ставит зависимости)

## Установка

```bash
uv sync
cp .env.example .env   # вписать OLLAMA_API_KEY
```

Переменные окружения:

| Переменная       | Пример                | Назначение                          |
|------------------|-----------------------|-------------------------------------|
| `OLLAMA_HOST`    | `https://ollama.com`  | Ollama Cloud или локальный Ollama   |
| `OLLAMA_API_KEY` | `...`                 | ключ Ollama Cloud (локально не нужен) |
| `LLM_MODEL`      | `gpt-oss:120b`        | модель                              |

## Запуск

```bash
uv run doc-extractor data/docs/01_invoice_almaty_trade.txt
```

## Eval

```bash
make eval                               # или: uv run python eval.py
uv run python eval.py --cache offline   # только сохранённые ответы, без API
uv run python eval.py --cache refresh   # заново спросить модель
```

Отчёт: точность по каждому полю; **галлюцинации** (заполнено, а в эталоне null) и **пропуски**
(null, а в эталоне значение) — раздельно; неверные значения; лишние/пропущенные позиции;
найдены ли противоречия; число повторных запросов и fallback. Те же метрики печатаются для
ответа модели **до grounding** — видно, сколько выдумок отсёк grounding.

## Структура

```
src/doc_extractor/
  schema.py     # pydantic-схема выхода
  prompt.py     # системный промпт и промпт повторного запроса
  llm.py        # клиент Ollama, дисковый кеш ответов, протокол для фейков
  extractor.py  # пайплайн: LLM -> валидация -> ретраи/fallback -> grounding
  grounding.py  # проверка каждого значения по исходному тексту
  textutil.py   # числа, пропись ru/kz, даты, OCR, БИН, нормализация
  evaluation.py # метрики eval
  cli.py        # CLI
data/docs/      # тексты документов
data/expected/  # эталонные JSON
eval.py         # мини-eval
```

## Как устроен пайплайн

```
текст -> LLM (structured output по JSON-схеме, temperature=0)
      -> json.loads + pydantic (extra=forbid, БИН ^\d{12}$, enum, дата)
         └─ не прошло -> повторный запрос с текстом ошибок (до 3 попыток)
            └─ не прошло 3 раза -> fallback: doc_type=unknown, все поля null,
               причина в warnings, valid=False, CLI выходит с кодом 2
      -> grounding: каждое значение ищется в исходном тексте без LLM
         └─ не найдено -> поле = null + warning
      -> арифметические проверки (только warnings)
```

**Grounding** ([grounding.py](src/doc_extractor/grounding.py)) — основная защита от галлюцинаций.
Модель может «уверенно выдумать», поэтому каждое поле проверяется детерминированно:

| Поле | Проверка |
|---|---|
| `supplier_bin` | 12 цифр подряд в тексте; если только после исправления OCR (`l→1`, `O→0`, `З→3`) — уверенность 0.6 + warning. Неверная контрольная цифра — warning (поле не обнуляется) |
| `doc_date` | дата есть в тексте (`12.11.2026`, `2 ноября 2026`, `09 қазан 2026`) |
| `total_amount`, `vat_amount`, `qty`, `price` | число есть в тексте цифрами (с учётом `2 100`, `1,116.50`, `10 441,38`) или прописью (ru/kz) |
| `currency` | в тексте есть маркер валюты (тенге/теңге/тг/₸/KZT, $/USD, €/EUR) |
| `doc_number` | есть в тексте (регистр, пробелы и похожие кириллица/латиница не важны) |
| `supplier_name`, названия позиций | ≥60% / ≥50% значимых слов названия есть в тексте; выдуманная позиция удаляется |

`field_confidence` = min(самооценка модели, уровень подтверждения): 1.0 — найдено как есть,
0.7 — только прописью, 0.6 — только после исправления OCR или частичное совпадение названия.

## Принятые решения (неоднозначности ТЗ)

- **Ложный null дешевле выдуманного значения.** Если значение не удаётся подтвердить текстом —
  обнуляем. Это осознанно повышает число пропусков ради снижения галлюцинаций.
- **Две разные даты** — `doc_date` = дата составления рядом с номером в заголовке; срок действия
  КП и срок оплаты датой документа не считаются. Противоречие — в `warnings`.
- **Две разные суммы «итого»** — берётся та, что сходится с суммой позиций (с учётом НДС), иначе
  первая; в `warnings` всегда предупреждение. Расхождение суммы прописью и цифрами grounding
  ловит сам.
- **`total_amount`** — итог к оплате (с НДС, если он указан). Если итог не написан (КП с
  перечнем цен), не суммируем — `null`.
- **«Без НДС» / «НДС не облагается»** — `vat_amount = null`, а не 0: числа в документе нет.
- **`supplier_name`** — поставщик/исполнитель, не покупатель. Если название на двух языках —
  русский вариант. БИН покупателя в `supplier_bin` не попадает.
- **`price`** — цена за единицу; из суммы строки не вычисляется.
- **«Шот-фактура № AKT-09»** (документ 3) — тип по заголовку (`invoice`), противоречие — в `warnings`.
- **Письмо, не являющееся счётом/КП/актом** (документ 10) — `doc_type=unknown`; номер и дата
  самого письма заполняются, поставщик — `null`.
- **LLM** — Ollama (`gpt-oss:120b` через Ollama Cloud, переключается переменными окружения на
  локальный Ollama). Ответы кешируются в `data/llm_cache/`, поэтому `eval.py --cache offline`
  работает без ключа и воспроизводит опубликованные цифры.

## Тестовый набор

| # | Документ | Что проверяет |
|---|---|---|
| 01–03 | из ТЗ | базовый счёт; КП без БИН/номера/итога; kz/ru + OCR в БИН + сумма прописью |
| 04 | счёт в USD | БИН покупателя рядом (ловушка), формат `1,116.50` |
| 05 | акт | **отсутствующие поля**: нет номера, даты, сумм, БИН поставщика |
| 06 | счёт | **сумма только прописью**, дата словами |
| 07 | КП | **смешанный казахско-русский текст**, EUR, `1 250,00` |
| 08 | счёт | **ошибки OCR** в БИН, номере, дате, суммах |
| 09 | счёт | **противоречия**: две даты, два «итого», пропись не совпадает с цифрами |
| 10 | письмо | ловушка галлюцинаций: компании и «счёт на оплату» упомянуты, но счёта нет |

[tests/test_dataset.py](tests/test_dataset.py) проверяет, что каждое значение каждого эталона
подтверждается текстом документа.
