# doc-extractor

Извлекает данные из текста счёта, коммерческого предложения или акта в JSON по фиксированной схеме.
Главная задача — не выдумывать то, чего нет в документе.

## Быстрый старт

Нужны Python 3.12 и [uv](https://docs.astral.sh/uv/getting-started/installation/).

```bash
git clone <repo-url>
cd <repo>
uv sync
uv run python eval.py --cache offline
```

Последняя команда прогоняет весь тестовый набор и печатает отчёт. Модель и ключ API не нужны:
используются сохранённые ответы модели из `data/llm_cache/`, а весь остальной пайплайн
(валидация, проверки, метрики) выполняется по-настоящему.

Тесты:

```bash
uv run pytest
```

## Запуск с живой моделью

1. Установить [Ollama](https://ollama.com/download) и скачать модель: `ollama pull qwen3:8b`
2. Создать `.env`: `cp .env.example .env`
3. Запустить:

```bash
uv run doc-extractor data/docs/01_invoice_almaty_trade.txt   # один документ
uv run python eval.py --cache refresh                         # весь набор заново
```

| Переменная | По умолчанию | Описание |
| --- | --- | --- |
| `OLLAMA_HOST` | `http://localhost:11434` | адрес Ollama (локальный или `https://ollama.com`) |
| `OLLAMA_API_KEY` | — | нужен только для Ollama Cloud |
| `LLM_MODEL` | `qwen3:8b` | модель |

## Как это работает

1. **LLM** получает текст и JSON-схему и отвечает строго по схеме.
2. **Валидация** (pydantic): типы, enum, БИН из 12 цифр, лишние поля запрещены.
   Если ответ не прошёл — модели отправляется повторный запрос с текстом ошибки (до 3 попыток).
   Если и это не помогло — возвращается безопасный результат: все поля `null`, причина в `warnings`,
   CLI завершается с кодом 2.
3. **Проверка по тексту.** Каждое значение ищется в исходном документе без участия LLM:
   суммы (цифрами и прописью на русском и казахском), даты, БИН (с исправлением OCR-ошибок
   вроде `l→1`, `O→0`), валюта, номер, названия. Не нашлось — поле становится `null`,
   в `warnings` пишется причина.
4. **Арифметика.** Если сумма позиций не сходится с итогом или сумма прописью не совпадает с
   цифрами — предупреждение в `warnings`.

`field_confidence`: 1.0 — значение найдено в тексте как есть, 0.7 — только прописью,
0.6 — только после исправления OCR.

## Принятые решения

- **Лучше пустое поле, чем выдуманное.** Всё, что не подтверждается текстом, обнуляется.
- **Две разные даты** — берётся дата рядом с номером документа. Срок действия КП и срок оплаты
  датой документа не считаются.
- **Две разные суммы «итого»** — берётся та, что сходится с суммой позиций (с учётом НДС), иначе первая.
- **`total_amount`** — итог к оплате с НДС. Если итог не написан, позиции не суммируются — `null`.
- **«Без НДС» / «НДС не облагается»** — `vat_amount = null`: числа в документе нет.
- **Поставщик** — тот, кто выставил документ. БИН покупателя в `supplier_bin` не попадает.
- **Название на двух языках** — берётся русский вариант.
- **Модель** — локальная `qwen3:8b` через Ollama: для Ollama Cloud нужны платные кредиты.

Во всех случаях противоречие записывается в `warnings`.

## Тестовый набор

10 документов в `data/docs/`, эталоны в `data/expected/`.

| # | Что проверяет |
| --- | --- |
| 01–03 | документы из задания |
| 04 | счёт в USD, рядом БИН покупателя |
| 05 | акт без номера, даты, сумм и БИН |
| 06 | сумма только прописью |
| 07 | смешанный казахско-русский текст, EUR |
| 08 | ошибки OCR в БИН, номере, дате и суммах |
| 09 | две разные даты и две разные суммы «итого» |
| 10 | письмо, а не счёт: проверка на выдумывание |

## Результаты (qwen3:8b)

| Поле | Точность | Галлюцинации | Пропуски |
| --- | --- | --- | --- |
| doc_type | 90% | 0 | 0 |
| supplier_name | 90% | 1 | 0 |
| supplier_bin | 100% | 0 | 0 |
| doc_number | 100% | 0 | 0 |
| doc_date | 80% | 0 | 2 |
| currency | 100% | 0 | 0 |
| total_amount | 100% | 0 | 0 |
| vat_amount | 100% | 0 | 0 |
| line_items (qty, price) | 100% | 0 | 0 |

- Галлюцинации — поле заполнено, хотя в эталоне `null`. Пропуски — `null`, хотя в эталоне есть значение.
- **Итого: 1 галлюцинация, 2 пропуска.** Без проверки по тексту было бы 3 галлюцинации:
  модель выдумала количество услуг в КП и перепутала казахские месяцы в двух датах.
- Повторных запросов и аварийных ответов не было.

Ошибки, которые остались:

- документ 10: письмо определено как счёт, автор письма записан как поставщик;
- документы 05 и 06: модель не выводит позиции без цены (4 позиции пропущены);
- модель пишет в `warnings` справки («НДС не указан»), а не только противоречия.

Первый прогон дал 13 пропусков: модель не выводила необязательные поля схемы. После того как
все поля сделаны обязательными (с допустимым `null`), пропусков стало 2.
Отчёт первого прогона — `docs/eval_run1_optional_fields.txt`.

## Что не сделано

- Проверка типа документа и роли поставщика без LLM (ошибка в документе 10).
- Промпт не настраивался под набор: на 10 документах улучшение не отличить от подгонки.
- Прогон на более сильной модели.

## Структура

```text
src/doc_extractor/
  schema.py      схема ответа
  prompt.py      промпты
  llm.py         клиент Ollama и кеш ответов
  extractor.py   пайплайн: LLM → валидация → повторы → проверка по тексту
  grounding.py   проверка значений по тексту
  textutil.py    разбор чисел, прописи, дат, БИН, OCR
  evaluation.py  метрики
  cli.py         командная строка
eval.py          запуск eval
data/            документы, эталоны, кеш ответов модели
tests/           автотесты
```
